Core concepts

What is load testing?

LOADConcurrent users increase10 → 100 → 1,000 virtual users
→
SYSTEMUnder real-world conditionsLog in → check → pay scenario
→
ANSWERMaximum capacity & SLAHow many before it slows down or fails?

Load testing is a category of performance testing that determines how a system performs under real-world conditions. It verifies that the existing infrastructure is sufficient, measures the maximum load it can handle, and determines its concurrent user capacity.

⏰
The last day before road tax prices go up — thousands of citizens log in at once. Can the portal handle that surge?
💡
Functional testing: “does it work?” · Performance testing: “does it hold up when many people arrive at once?”

Load testing jawab: berapa ramai pengguna sebelum sistem slow atau gagal?

  • Naikkan pengguna serentak: 10 → 100 → 1,000 virtual users.
  • Senario dunia sebenar: log masuk, check, bayar.
  • Jawapan dicari: kapasiti maksimum dan SLA.
  • Functional test: "berfungsi ke?"; performance test: "tahan ke bila ramai?"

Contoh: Hari terakhir sebelum harga cukai jalan naik — beribu log masuk serentak. Kalau portal gagal, satu negara nampak.

Fully open-source software built on Java for load testing and measuring performance. It evaluates functional behavior under load.

Originally for web applications — now covers APIs, databases, FTP, JMS and much more.

Extensible

Large community

Ethics & the law

Rule number one: localhost only

⛔
JMeter is a load generator. From the server's point of view, 200 JMeter threads look the same as 200 attackers. Load testing without written permission = a denial-of-service (DoS) attack — even if your intentions are good.

✅ Allowed

  • Course mock: http://localhost:3000 (sut/)
  • Staging owned by your organisation with written permission: scope, hosts, time window, load level
  • Synthetic data only

❌ Prohibited

  • The real JPJ portal / any public site without permission
  • “Just a quick try” on production during office hours — or at night
  • Real citizens' IC numbers / registration numbers in a CSV
HABIT

Before Start ▶: open HTTP Request Defaults — Server = localhost, Port = 3000. Every time, every plan.

Rule nombor satu: localhost sahaja.

  • 200 thread JMeter nampak sama macam 200 penyerang.
  • Load test tanpa kebenaran bertulis = serangan DoS, walaupun niat baik.
  • Dibenarkan: mock kursus, staging dengan kebenaran bertulis, data sintetik.
  • Dilarang: portal JPJ sebenar, "try sekejap" di production, IC rakyat sebenar.
  • Dapatkan kelulusan pemilik sistem, maklumkan NOC/SOC, tetapkan siapa tekan Stop.

Soalan: Kawan ajak test portal sebenar dengan 50 threads? Tolak — saiz beban tak ubah status undang-undang.

Anatomy of a performance test: load, scenario, metrics, criteria

LOAD

How many?

Concurrent users & arrival pattern (ramp-up).

SCENARIO

Doing what?

A sequence of requests that mimics real users.

METRICS

What is measured?

Response time, throughput, error rate.

CRITERIA

Passes when?

SLA / NFR — written pass/fail thresholds.

MetricShort meaningWhere you see it today

ThroughputNumber of requests completed per second (req/s)Summary / Aggregate Report
Error %Percentage of failed samples — HTTP 4xx/5xx, network, or a failed assertionSummary / Aggregate Report

Setiap performance test ada empat komponen: Load, Scenario, Metrics, Criteria.

  • Load: berapa ramai — pengguna serentak dan ramp-up.
  • Scenario: turutan request yang tiru pengguna sebenar.
  • Metrics: response time (ms), throughput (request/second), Error %, concurrency.
  • Criteria: SLA atau NFR — threshold pass/fail bertulis (dalami Hari 2).

Soalan: Portal ambil 3 second untuk satu user — dah gagal? Bergantung pada kriteria bertulis; tanpa NFR, tak boleh kata pass atau fail.

Day 1 · S1 — Test types

Five types of performance test

LOAD

Expected load

Handles normal/peak load? Verify the SLA.

STRESS

Where does it break?

Add users until it fails.

SPIKE

Sudden surge

Traffic spikes — does it recover?

SOAK

Long duration

Moderate load for hours — memory leak?

SCALABILITY

Add resources

Same load, compare configurations.

📈
Load: 1,000 road tax renewals an hour on a normal day.
⚡
Spike: the last night before prices go up — 10× traffic within 5 minutes.
🕒
Soak: the portal stays up for 72 hours over a long holiday without a restart.

Lima jenis performance test, setiap satu jawab soalan berbeza.

  • Load: beban dijangka — 1,000 pembaharuan cukai jalan sejam.
  • Stress: tambah users sampai sistem pecah.
  • Spike: trafik 10× dalam 5 minit — boleh pulih ke tak?
  • Soak: beban sederhana berjam-jam, contoh 72 jam — kesan memory leak.
  • Scalability: beban sama, banding konfigurasi.

Contoh: Malam terakhir sebelum harga naik, trafik 10× — itu Spike. Kursus fokus Load dan Stress.

Scope by position

Config, Timer, Assertion & Listener affect every sampler at the same level or deeper. Under the Thread Group → all samplers. A child of one sampler → only that sampler.

Two surprises for beginners

(1) Timers run before the sampler. (2) A timer under a Thread Group with 3 samplers pauses 3 times per iteration — once for each sampler in its scope.

🐞
Misplaced elements are the most common source of bugs. The visual order in the tree does not change the execution order — except among elements of the same type.

JMeter execute elemen ikut susunan tetap, dan scope ikut kedudukan.

DURATION ASSERTION

Too slow = failed

Duration in milliseconds 2000 — samples > 2 s are marked failed even with code 200.

CONCEPT

Assertions change what “failed” means

Without assertions, only network/HTTP errors count. With assertions, wrong content or too slow also go into Error %.

💸
Assertions cost CPU on every sample. Prefer Substring / simple JSON Assertions.

Response code 200 tak semestinya betul — assertion wajib.

  • Server bagi 200 dengan {"ralat":"Sistem sibuk"}? Tanpa assertion, JMeter kira pass.
  • Response Assertion anak HTTP Request: Text Response, Substring, pattern amaun.
  • Negative test (nak 404): Response Code dengan Ignore Status.
  • Duration Assertion 2000 ms: lebih 2 s = gagal walaupun 200.
  • Assertion guna CPU setiap sample — pilih yang ringkas.
Day 1 · S3 — Step 6

Timers: think time makes the load realistic

CONSTANT TIMER

Fixed pause

Thread Delay — e.g. 300 ms per sampler.

UNIFORM RANDOM TIMER

Uniform random

Offset 500 + Random Max 1000 → 0.5–1.5 s (plan 03).

GAUSSIAN RANDOM TIMER

Normal distribution

Offset 1000 ± Deviation 300 ms — most realistic.

ESTIMATE

throughput ≈ threads ÷ (response time + think time)

20 threads · no timer~200 req/s20 ÷ 0.1 s
20 threads · 300 ms timer~50 req/s20 ÷ (0.1 + 0.3) s
⏱️
Timer time is not counted in response time. Average does not rise — what drops is throughput.

Timer bagi think time, dan think time buat beban realistik.

  • Constant Timer: pause tetap, contoh 300 ms.
  • Uniform Random: offset 500 + max 1000 = 0.5–1.5 s (plan 03).
  • Gaussian: 1000 ± 300 ms — paling realistik.
  • Anggaran: throughput ≈ threads ÷ (response time + think time).
  • 20 threads: tanpa timer ~200 req/s; dengan 300 ms ~50 req/s.

Soalan: Tambah timer 1000 ms — Average naik 1000 ms? Tak; throughput turun, masa timer tak dikira dalam response time.

Day 2 · S4 — Load model & Little's Law

User counts are calculated, not guessed

N = X × (R + Z)

N concurrent users · X throughput (trans/s) · R response time (s) · Z think time per iteration (s)

eJPJ WORKED EXAMPLE · TRAINING ASSUMPTIONS, NOT OFFICIAL DATA
Peak-hour volume36,000 renewals / 1 hour
Target rate X36,000 ÷ 3,600 = 10 transactions/s
HTTP requests10 × 4 = 40 requests/s
R (conservative = NFR limit)2 s
Z list 15 + quote 20 + pay 2358 s
N10 × (2 + 58) = 600 concurrent users
VERIFIED IN THE LAB · PLAN 07

Z ≈ 4 s (0.5–1.5 s × 4) · 50 users

R1: X = 10.46 R = 0.446 s Z = 4.0 s N = 10.46 × 4.446 ≈ 46.5 R3: X = 5.78 R = 3.954 s Z = 4.0 s N = 5.78 × 7.954 ≈ 46.0 average active threads ≈ 45.8 (ramp-up 10 s)
↔️
Two directions: (1) planning — target X → N threads; (2) checking a report — X × (R + Z) ≠ average active threads → timers not running, threads died early, or generator overloaded.
🧮
Quiz: 18,000/hour, R = 2 s, Z = 28 s → X = 5 → N = 150. Units: everything in seconds.

Bilangan users dikira dengan Little's Law, bukan diteka.

  • N = X × (R + Z) — semua dalam saat.
  • Andaian latihan: 36,000 sejam ÷ 3,600 = X 10 trans/s.
  • R 2 s, Z 58 s: N = 10 × 60 = 600 concurrent users.
  • Concurrent users bukan users berdaftar.
  • Lab: R1 ≈ 46.5, R3 ≈ 46.0, threads ≈ 45.8 — X turun bila R naik.

Contoh: X × (R + Z) tak sama dengan active threads? Timer tak jalan, threads mati awal, atau generator overload.

4 · STRESS

Where is the knee point?

Step up -Jpengguna=50 → 100 → 150 …

5 · SPIKE

Sudden surge — does it recover?

-Jpengguna=150 -Jrampup=1

6 · SOAK

Stable over the long term?

-Jpengguna=35 -Jtempoh=1800 (real: hours)

🧭
Always baseline first. Without a baseline, you can't tell whether 1% errors are caused by load — or already exist at 1 user (our SUT's ERROR_RATE 1%).

Turutan run: smoke → baseline → load → stress → spike → soak.

  • Smoke: plan 05, 10 × 2, 0 error functional.
  • Baseline 5 users = angka rujukan; Load 50 users = PASS/FAIL ikut NFR.
  • Stress 50, 100, 150 — cari knee point.
  • Spike 150 users ramp-up 1 s; Soak 35 users 1800 s.
  • Stress dan spike paling berisiko — perlu time window dan prosedur stop.

Soalan: Kenapa baseline dulu? Tanpa dia, kita tak tahu 1% error tu sebab beban atau dah ada pada 1 user.

jmeter -n exits with code 0 even when samples fail. Our R1: p95 583 ms, error 1.0033% → FAIL (right on the limit, synthetic 500s). Alternatives: Taurus (bzt) passfail, Jenkins Performance plugin.
DISTRIBUTED

-R w1,w2 -Gpengguna=100

Each worker (jmeter-server) runs the entire Thread Group → 100 × 2 = 200. -G sends properties to workers; the CSV must exist on every worker.

Backend Listener → InfluxDB
