Alat kita

Apa itu Apache JMeter — dan kenapa ia?

Perisian open-source sepenuhnya berasaskan Java untuk menguji beban dan mengukur prestasi. Ia menilai functional behavior di bawah beban.

Asalnya untuk aplikasi web — kini merangkumi API, pangkalan data, FTP, JMS dan banyak lagi.

⚠️
JMeter bukan pelayar: ia tidak menjalankan JavaScript halaman. Ia menghantar permintaan HTTP — sama seperti 1,000 pelanggan serentak.

Percuma

Tiada kos lesen.

Pelbagai jenis ujian

Load, stress, spike, soak dalam satu alat.

Merentas platform

Windows, macOS, Linux — asal ada Java.

Boleh diubah suai

JSR223 Groovy, fungsi, plugin.

Etika & undang-undang

Peraturan nombor satu: localhost sahaja

⛔
JMeter ialah penjana beban. Dari sudut pelayan, 200 thread JMeter kelihatan sama seperti 200 penyerang. Ujian beban tanpa kebenaran bertulis = serangan penafian perkhidmatan (DoS) — walaupun niat anda baik.

✅ Dibenarkan

  • Mock kursus: http://localhost:3000 (sut/)
  • Staging milik organisasi anda dengan kebenaran bertulis: skop, hos, tetingkap masa, paras beban
  • Data sintetik sahaja

❌ Dilarang

  • Portal JPJ sebenar / mana-mana laman awam tanpa kebenaran
  • “Cuba sikit je” pada production waktu pejabat — atau waktu malam
  • No. KP / nombor pendaftaran rakyat sebenar dalam CSV
TABIAT

Sebelum Start ▶: buka HTTP Request Defaults — Server = localhost, Port = 3000. Setiap kali, setiap plan.

Ini slaid paling penting kursus. Dalam organisasi kerajaan: dapatkan kelulusan bertulis pemilik sistem dan pasukan infrastruktur/keselamatan, maklumkan NOC/SOC sebelum larian, dan tetapkan siapa yang boleh menekan "Stop".

Soalan Kuiz S1: rakan cadang "uji sikit" portal JPJ sebenar dengan 50 thread. Jawapan: tolak. Saiz beban atau waktu tidak mengubah status undang-undang.

Hari 1 · S3 — Langkah 6

Timer: think time menjadikan beban realistik

CONSTANT TIMER

Jeda tetap

Thread Delay — cth. 300 ms setiap sampler.

UNIFORM RANDOM TIMER

Rawak seragam

Offset 500 + Random Max 1000 → 0.5–1.5 s (plan 03).

GAUSSIAN RANDOM TIMER

Taburan normal

Offset 1000 ± Deviation 300 ms — paling realistik.

ANGGARAN

throughput ≈ threads ÷ (masa respons + think time)

20 thread · tanpa timer~200 req/s20 ÷ 0.1 s
20 thread · timer 300 ms~50 req/s20 ÷ (0.1 + 0.3) s
⏱️
Masa timer tidak dikira dalam masa respons. Average tidak naik — yang turun ialah throughput.

Thread Group → Add → Timer → Constant Timer, Delay 300. Throughput tanpa think time tidak realistik dan membebankan sistem secara palsu.

Soalan Kuiz S3 #2: tambah Constant Timer 1000 ms pada 20 thread → throughput turun, Average tidak naik ~1000 ms.

Hari 2 · S4 — Model beban & Little's Law

Bilangan pengguna dikira, bukan diteka

N = X × (R + Z)

N pengguna serentak · X throughput (trans/s) · R masa respons (s) · Z think time satu lelaran (s)

CONTOH KERJA eJPJ · ANDAIAN LATIHAN, BUKAN DATA RASMI
Volum jam puncak36,000 pembaharuan / 1 jam
Kadar sasaran X36,000 ÷ 3,600 = 10 transaksi/s
Permintaan HTTP10 × 4 = 40 permintaan/s
R (konservatif = had NFR)2 s
Z senarai 15 + sebut harga 20 + bayar 2358 s
N10 × (2 + 58) = 600 pengguna serentak
DISAHKAN DENGAN MAKMAL · PLAN 07

Z ≈ 4 s (0.5–1.5 s × 4) · 50 pengguna

R1: X = 10.46 R = 0.446 s Z = 4.0 s N = 10.46 × 4.446 ≈ 46.5 R3: X = 5.78 R = 3.954 s Z = 4.0 s N = 5.78 × 7.954 ≈ 46.0 purata thread aktif ≈ 45.8 (ramp-up 10 s)
↔️
Dua arah: (1) merancang — X sasaran → N threads; (2) menyemak laporan — X × (R + Z) ≠ purata thread aktif → timer tidak jalan, thread mati awal, atau penjana sesak.
🧮
Kuiz: 18,000/jam, R = 2 s, Z = 28 s → X = 5 → N = 150. Unit: semua dalam saat.

Momen kunci #6: "Little's Law membolehkan anda menyemak laporan orang lain dalam 30 saat." R1 dan R3: N sama (≈ 46), R naik, X turun — inilah sebab throughput R3 jatuh 45%.

Salah faham lazim: "bilangan pengguna = pengguna berdaftar" — tidak, pengguna serentak = X × (R + Z). Isu lab: N sangat kecil kerana Z dilupakan; N berjuta kerana unit minit/saat bercampur. Semakan kendiri #5: 50 ÷ 4.45 ≈ 11.2 trans/s dijangka.

Kawal kadar: Constant / Precise Throughput Timer
