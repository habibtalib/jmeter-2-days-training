Core concepts

What is load testing?

LOADConcurrent users increase10 → 100 → 1,000 virtual users
→
SYSTEMUnder real-world conditionsLog in → check → pay scenario

ANSWERMaximum capacity & SLAHow many before it slows down or fails?

Load testing is a category of performance testing that determines how a system performs under real-world conditions. It verifies that the existing infrastructure is sufficient, measures the maximum load it can handle, and determines its concurrent user capacity.

⏰
The last day before road tax prices go up — thousands of citizens log in at once. Can the portal handle that surge?
💡
Functional testing: “does it work?” · Performance testing: “does it hold up when many people arrive at once?”

Ethics & the law

Rule number one: localhost only

⛔
JMeter is a load generator. From the server's point of view, 200 JMeter threads look the same as 200 attackers. Load testing without written permission = a denial-of-service (DoS) attack — even if your intentions are good.

✅ Allowed

  • Course mock: http://localhost:3000 (sut/)
  • Staging owned by your organisation with written permission: scope, hosts, time window, load level
  • Synthetic data only

❌ Prohibited

  • The real JPJ portal / any public site without permission
  • “Just a quick try” on production during office hours — or at night
  • Real citizens' IC numbers / registration numbers in a CSV
HABIT

Before Start ▶: open HTTP Request Defaults — Server = localhost, Port = 3000. Every time, every plan.

Ini slaid paling penting dalam kursus. Dalam organisasi kerajaan: dapatkan kelulusan bertulis daripada pemilik sistem dan pasukan infrastruktur/keselamatan, maklumkan NOC/SOC sebelum run, dan tetapkan siapa yang boleh tekan "Stop".

Soalan kuiz S1: rakan sekerja cadang "test sekejap" portal JPJ sebenar dengan 50 threads. Jawapan: tolak. Saiz beban atau waktu tak ubah status undang-undang.

Scope by position

Config, Timer, Assertion & Listener affect every sampler at the same level or deeper. Under the Thread Group → all samplers. A child of one sampler → only that sampler.

Two surprises for beginners

(1) Timers run before the sampler. (2) A timer under a Thread Group with 3 samplers pauses 3 times per iteration — once for each sampler in its scope.

🐞
Misplaced elements are the most common source of bugs. The visual order in the tree does not change the execution order — except among elements of the same type.

Objektif O5. Contoh semak kendiri: Constant Timer 300 ms bawah Thread Group dengan 3 HTTP Requests → lebih kurang 900 ms pause setiap iteration. Kalau nak pause sekali je, jadikan timer tu anak kepada satu sampler.

Soalan kuiz S2 #2: assertion yang jadi anak sampler A — sampler B (adik-beradik) tak di-check.

🚦

DURATION ASSERTION

Too slow = failed

Duration in milliseconds 2000 — samples > 2 s are marked failed even with code 200.

Day 1 · S3 — Step 6

Timers: think time makes the load realistic

CONSTANT TIMER

Fixed pause

Thread Delay — e.g. 300 ms per sampler.

UNIFORM RANDOM TIMER

Uniform random

Offset 500 + Random Max 1000 → 0.5–1.5 s (plan 03).

GAUSSIAN RANDOM TIMER

Normal distribution

Offset 1000 ± Deviation 300 ms — most realistic.

ESTIMATE

throughput ≈ threads ÷ (response time + think time)

20 threads · no timer~200 req/s20 ÷ 0.1 s
20 threads · 300 ms timer~50 req/s20 ÷ (0.1 + 0.3) s
⏱️
Timer time is not counted in response time. Average does not rise — what drops is throughput.

Thread Group → Add → Timer → Constant Timer, Delay 300. Throughput tanpa think time tak realistik dan bagi beban tiruan pada sistem.

Day 2 · S3 — Multi-site agents · pitfalls

Before you trust a multi-site report

  • Clock sync (NTP) on every agent — timestamps from different clocks skew the Over Time graphs
  • CSV on every agent (same path) — and split the data so sites don't log in as the same user
  • Controller bottleneck — it receives every sample; keep the sample sender mode StrippedBatch (default), no GUI listeners
  • Firewall / RMI ports open both ways · SSL keystore on all, or SSL off on all
  • Same JMeter & Java versions (and plugins) on controller and agents
  • Results bandwidth — samples travel site → controller during the test; don't saturate the link you are measuring
  • Matching JTL headers before merging · users = threads × agents stated in the report

Day 2 · S4 — Load model & Little's Law

User counts are calculated, not guessed

N = X × (R + Z)

N concurrent users · X throughput (trans/s) · R response time (s) · Z think time per iteration (s)

eJPJ WORKED EXAMPLE · TRAINING ASSUMPTIONS, NOT OFFICIAL DATA
Peak-hour volume36,000 renewals / 1 hour
Target rate X36,000 ÷ 3,600 = 10 transactions/s
HTTP requests10 × 4 = 40 requests/s
R (conservative = NFR limit)2 s
Z list 15 + quote 20 + pay 2358 s
N10 × (2 + 58) = 600 concurrent users
VERIFIED IN THE LAB · PLAN 07

Z ≈ 4 s (0.5–1.5 s × 4) · 50 users

R1: X = 10.46 R = 0.446 s Z = 4.0 s N = 10.46 × 4.446 ≈ 46.5 R3: X = 5.78 R = 3.954 s Z = 4.0 s N = 5.78 × 7.954 ≈ 46.0 average active threads ≈ 45.8 (ramp-up 10 s)
↔️
Two directions: (1) planning — target X → N threads; (2) checking a report — X × (R + Z) ≠ average active threads → timers not running, threads died early, or generator overloaded.
🧮
Quiz: 18,000/hour, R = 2 s, Z = 28 s → X = 5 → N = 150. Units: everything in seconds.

Momen kunci #6: "Little's Law boleh bantu anda check report orang lain dalam 30 saat." R1 dan R3: N sama (≈ 46), R naik, X turun — sebab tu throughput R3 jatuh 45%.

Salah faham biasa: "bilangan user = user berdaftar" — tak, concurrent users = X × (R + Z). Masalah lab: N terlalu kecil sebab lupa Z; N berjuta-juta sebab campur minit/saat. Semak kendiri #5: 50 ÷ 4.45 ≈ 11.2 trans/s dijangka.

Where is the knee point?

Stable over the long term?
